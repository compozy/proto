# ADR-002: Prebuilt, isolated shell; prototypes in consumer iframes

## Status

Proposed

## Date

2026-10-30

## Context

All three copies render the shell with the host app's design system (`@reload/ui`, `@acme/ui`,
`@compozy/ui`) and compile it inside the app's Vite config, filtering plugins by name. A library cannot
depend on the consumer's components or styles.

## Decision

The shell is a separate React app built at package build time into `dist/shell` with its own React,
vendored BnUI components and compiled Tailwind CSS. The Vite plugin serves it at `/` (dev and build) and
exposes a render host at `/__proto/render/<slug>` compiled by the consumer's Vite with the consumer's
plugins. Shell and render host communicate only through URL parameters and a postMessage handshake
trusted by source window and origin (the React Cosmos UI/renderer split).

## Alternatives Considered

### Alternative 1: Shell compiled in the consumer's Vite

- **Pros**: one bundle, shared React.
- **Cons**: consumer's Tailwind/PostCSS/React Compiler apply to shell code; style collisions; the consumer
  must allow-list the package in its sources.
- **Why rejected**: it is today's coupling.

### Alternative 2: Shadow DOM shell in the same document

- **Pros**: one document.
- **Cons**: portals (dialogs, popovers) escape the shadow root; consumer global CSS still leaks in.
- **Why rejected**: brittle for a tool full of overlays.

## Consequences

### Positive

- The shell looks identical in every project; consumers never compile it.

### Negative

- Two React copies in the page (shell + each iframe).

### Risks

- Iframe count on the flow canvas → existing preview queue (≤ 3 loading, ≤ 12 kept).

## Implementation Notes

Shell components come from the visual contract (`proto-shell` draft); BnUI sources vendored under
`src/shell/ui` with provenance headers.
