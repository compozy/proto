# ADR-004: proto.config.ts + proto.canvas.tsx; one plugin per build context

## Status

Proposed (revised after peer review round 1)

## Date

2026-10-30

## Context

Stack apps opt in with `gallery.config.ts`, `vite.presentation.ts` and `preview/{canvas.tsx,gallery.css}`;
`vite.presentation.ts` is also Storybook's `viteConfigPath` and is imported by `vitest.config.ts`, carrying the
presentation guard. reloaddev hardcodes specs/roles; CompozyOS hardcodes paths and matches guard modules by
regex families. Storybook stays (Non-Goal to replace it).

## Decision

Two consumer files: `proto.config.ts` (data) and `proto.canvas.tsx` (`Canvas`, optional `Frame`). Two
plugin factories with fixed behavior per context:

- `proto()` in `vite.config.ts`: in the app's own `vite dev`/`vite build` it does only the production
  boundary; inside `proto dev`/`proto build` (render mode, set by the CLI) it adds registry, virtual modules,
  source tags, network guard and the render host.
- `protoPresentation()` for Storybook `viteFinal` and Vitest: network guard for graphs rooted at stories and
  prototypes, optional source tags — the replacement for `vite.presentation.ts`.

Guards accept module ids, globs or RegExp and apply only to graphs rooted at prototypes, drafts and stories.
`proto migrate` lists `vite.presentation.ts` and `preview/` as deletable only after the consumer switched
Storybook and Vitest and its own gates pass.

## Alternatives Considered

### Alternative 1: Keep `gallery.config.ts` and `preview/`

- **Why rejected**: three files for one concern; migration is automated.

### Alternative 2: One plugin that inspects `process.argv` to guess the context

- **Why rejected**: implicit; Storybook and Vitest need a distinct, explicit entry.

## Consequences

### Positive

- Two files to adopt; Storybook keeps its guard; production builds stay untouched except for the boundary.

### Negative

- Consumers edit their Storybook and Vitest configs once.
