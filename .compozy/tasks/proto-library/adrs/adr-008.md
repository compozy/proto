# ADR-008: Separate render origin and a typed shell ⇄ render protocol

## Status

Proposed

## Date

2026-10-30

## Context

Prototypes run arbitrary consumer code, often written by agents. On the same origin as the shell and review
API, a prototype's `fetch` carries the reviewer's origin and cookies and could approve, mint credentials or
comment as the reviewer (O-B004). The current picker reads the iframe's document directly, which a strict
"postMessage only" boundary cannot replace without a protocol (A-B007).

## Decision

Render prototypes on a separate origin: dev `127.0.0.1:<port+1>` (default 4401), remote `renderOrigin` (a
separate host, e.g. `render.proto.acme.com`). The render origin never holds review cookies or credentials;
review writes require the shell origin (dev) or `publicOrigin` plus `X-Proto-Request: 1` (remote). Remote
render assets are protected by short-lived HMAC render tickets exchanged for a render-host cookie.

Picking and anchoring move into the render host; the shell drives them through a versioned protocol
(`ready`, `error`, `context`, `pick:start|cancel|result`, `anchors:watch`, `anchors`, `scroll:to`) with frame
nonces and origin checks on both sides (`_spec.md` § Shell ⇄ render protocol). Static read-only builds may
serve the render host from the same host because they accept no writes.

## Alternatives Considered

### Alternative 1: Same origin + CSRF token held by the shell

- **Pros**: one origin, simpler dev setup; picker code moves unchanged.
- **Cons**: same-origin script can read the shell's DOM and token; advisory only.
- **Why rejected**: not a real boundary for remote approval.

### Alternative 2: Sandboxed iframe without `allow-same-origin`

- **Cons**: breaks the consumer app (storage, cookies, some libraries) inside prototypes.
- **Why rejected**: prototypes must run the real app code faithfully.

## Consequences

### Positive

- Prototype code cannot act as the reviewer; the protocol is testable and versioned.

### Negative

- Two ports in dev; the picker is rewritten as render-host code.

### Risks

- Picker fidelity (source chain, region contents) — covered by the comment E2E (click, region, keyboard,
  scroll, state change).
