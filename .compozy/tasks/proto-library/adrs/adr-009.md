# ADR-009: Per-key review file v3, lock protocol and transactions

## Status

Proposed

## Date

2026-10-30

## Context

The real v2 file is `{ version: 2, slug, comments }` with string ids, `thread`, string authors, `at`,
`updatedAt`/`resolvedAt`; CompozyOS adds `sequence`; reloaddev has v1 files. The first draft claimed
"v2 unchanged" while defining another shape and kept approval in a separate file, outside the lock (O-B001,
O-B003, A-B001, A-B003). The cited lock reclaimed by age only and released unconditionally (O-B003, A-B002).

## Decision

1. **Version 3 = v2 + `sequence` + `review` + `events`** in the same per-key file (`proto/review/<key>.json`);
   comment and message fields keep their v2 names; remote identity fields are optional additions. Readers
   upgrade v1 and v2 losslessly (preserving unknown fields under `extra`); writers write v3.
2. **One critical section per key** for every mutation, including approval and auto-reopen. Local storage is
   **single-host**. Lock: `mkdir <key>.lock/` with `owner.json { token, pid, processStartedAt, hostId }`. A
   lock is reclaimed only when its owner is provably dead (same host and pid not running, or pid reused —
   different start time); live owners are never evicted, other-host locks never reclaimed automatically
   (`proto review unlock --force` is the manual recovery). Reclaimers serialize through
   `<key>.lock.takeover/` and re-check the observed token before renaming the stale lock to a tombstone.
   The takeover directory has the same owner metadata and dead-owner-only reclamation rule; age never proves owner death.
   Because only dead owners lose their lock, no evicted writer can publish afterwards — no fencing token is
   needed. Release is token-matched; waits are asynchronous and bounded (`key_busy`).
3. **Postgres**: one transaction per mutation holding `proto_keys … FOR UPDATE`; `next_comment` is the
   sequence; events and `open_count` persisted; pending claims are single-row conditional updates.

## Alternatives Considered

### Alternative 1: Keep approval in a separate file with its own lock

- **Why rejected**: needs cross-file recovery for auto-reopen and open counts.

### Alternative 2: SQLite for local review data

- **Pros**: transactions for free.
- **Cons**: binary file; review data no longer reviewable in PRs.
- **Why rejected**: plain files in the repository are a product requirement.

## Consequences

### Positive

- Every user-visible transition is atomic; history survives migration; ids never reused.

### Negative

- Files grow with events; acceptable (events are small and per key).

### Risks

- Network filesystems and checkouts shared across machines are unsupported (single-host contract); a lock
  left by another host needs the manual `unlock`.
- Round 2 (O-B011, A-B011) showed that age-based reclamation plus a pre-publish token check cannot fence a
  paused writer; the dead-owner-only rule removes that case instead of adding fencing machinery.
